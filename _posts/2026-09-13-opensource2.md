## 개요

[이전 글](https://ar9988.github.io/posts/opensource1/)에서는 Glance 날씨 위젯이 프로세스 재시작 후 로딩 화면에 머무는 문제를 분석했습니다.

원인은 데이터 초기화 위치였습니다. 기존 위젯이 남아 있는 상태에서 프로세스가 다시 생성되면 `onEnabled()`가 호출되지 않았고, 여기에 있던 데이터 로딩도 실행되지 않았습니다. 초기화를 `provideGlance()`로 옮긴 뒤, 맥북의 Android 11 에뮬레이터에서 정상적으로 날씨가 표시되는 것을 확인했습니다.

다른 환경에서도 같은 수정으로 문제가 해결되는지 확인하고 싶었습니다. 데스크탑에서 Android 13, 14, 15, 17 등 여러 버전의 에뮬레이터로 테스트를 이어갔습니다.

그런데 수정한 코드에서도 위젯이 로딩 화면에 머물렀습니다.

처음에는 Android 버전에 따른 차이를 의심했습니다. 그래서 이전에 정상 동작을 확인했던 Android 11 에뮬레이터도 데스크탑에서 실행해봤습니다. **같은 Android 11에서도 문제가 일관되게 해결되지는 않았습니다.**

이제 Android 버전 차이만으로 설명할 수 없었습니다. 맥북에서 확인한 성공과 데스크탑에서 관찰한 실패 사이에 어떤 차이가 있는지 확인해야 했습니다.

초기화 수정이 실제로 효과가 있었던 것인지, 다른 조건이 결과에 영향을 준 것인지 구분하기 위해 성공한 실행과 실패한 실행의 로그를 다시 비교했습니다.

## 이전에 고친 문제

기존 코드에서는 `onEnabled()`에서 날씨 데이터를 초기화했습니다.

```text
첫 위젯 추가
→ onEnabled()
→ 날씨 데이터 초기화
→ Available
```

하지만 위젯이 이미 존재하는 상태에서 프로세스가 다시 생성되면 상황이 달라졌습니다. 메모리에 저장된 날씨 상태는 초기값인 `Loading`으로 돌아갔지만, `onEnabled()`는 다시 호출되지 않았습니다.

```text
기존 위젯을 유지한 채 프로세스 재생성
→ 메모리의 날씨 상태는 Loading으로 초기화
→ onUpdate()
→ provideGlance()
→ 데이터 초기화가 실행되지 않음
→ Loading 유지
```

그래서 데이터를 준비하는 코드를 `provideGlance()`로 옮겼습니다.

```kotlin
override suspend fun provideGlance(
    context: Context,
    id: GlanceId,
) {
    WeatherRepo.updateWeatherInfo()

    provideContent {
        Content()
    }
}
```

이 수정은 `provideGlance()`가 실행되는 경로에서 초기화 누락을 보완합니다.

그런데 데스크탑에서 실패한 실행도 이 경로를 거쳤을까요?

## 같은 로딩 화면인데, 실행된 코드가 달랐다

추가 분석은 데스크탑의 Android 11 에뮬레이터에서 진행했습니다. 같은 환경에서도 성공과 실패가 모두 관찰돼 두 실행을 비교할 수 있었기 때문입니다.

재현 설정은 이전과 같았습니다.

- Android Studio의 **Always install with package manager** 활성화
- Launch Options를 **Nothing**으로 설정
- 홈 화면에 기존 위젯을 유지한 채 재설치

처음에는 날씨가 표시되면 성공, 로딩 표시가 계속 돌면 실패로 판단했습니다. 하지만 로그를 확인하니 같은 로딩 화면이어도 실행 과정은 달랐습니다.

이전 글의 실패에서는 `onUpdate()`와 `provideGlance()`가 호출됐습니다. 위젯 코드는 실행됐고, 그 안에서 데이터 초기화가 빠져 있었습니다.

반면 이번 실패 기록에는 **위젯을 갱신할 새 앱 프로세스 자체가 시작되지 않은 경우**가 있었습니다.

`provideGlance()`가 실행되지 않았다면, 그 안에 추가한 초기화 코드도 실행될 수 없습니다. 로딩 함수 내부만 살펴봐서는 이 실패를 설명할 수 없었습니다.

그래서 앱 로그와 함께 Android Studio의 설치 로그, 시스템의 위젯 업데이트 브로드캐스트 기록을 확인했습니다.

## 성공한 실행에도 강제 종료는 있었다

조사한 Android Studio 재설치 과정에서는 설치 후 앱에 대한 `force-stop`, 즉 강제 종료가 관찰됐습니다.

처음에는 이것이 실패를 설명하는 것처럼 보였습니다. 하지만 **성공한 실행에도 강제 종료가 있었습니다.**

강제 종료의 유무만으로는 결과를 구분할 수 없었습니다. 차이는 강제 종료와 위젯 업데이트가 대기열에 들어가는 순서였습니다.

직접 실행한 네 사례를 비교했습니다. 업데이트 대기열 진입 시각은 `dumpsys activity broadcasts`의 `enqueueClockTime`에서 확인했습니다.

| 시도 | 설치 후 마지막 강제 종료 | 업데이트 대기열 진입 | 결과 |
|---|---|---|---|
| 1 | 23:04:54.372 | 23:04:54.533 | 성공 |
| 2 | 23:06:29.787 | 23:06:29.761 | 실패 |
| 3 | 23:07:39.042 | 23:07:39.037 | 실패 |
| 4 | 23:08:37.266 | 23:08:37.291 | 성공 |

성공한 두 사례에서는 강제 종료 **이후** 업데이트가 대기열에 들어갔습니다. 이후 브로드캐스트가 전달되고 새 프로세스가 시작돼 날씨 콘텐츠를 제공했습니다.

실패한 두 사례에서는 순서가 반대였습니다. 업데이트가 대기열에 들어간 뒤 각각 26ms, 5ms 후에 강제 종료가 발생했습니다.

실패 기록에도 업데이트 요청은 남아 있었습니다. 하지만 전달 시각과 수신자 항목이 없었고, 새 앱 프로세스도 시작되지 않았습니다.

**업데이트 요청이 만들어진 것과, 실제로 위젯 코드가 실행된 것은 별개였습니다.**

## 강제 종료 시점만 바꿔봤다

네 사례에서는 실행 순서와 결과가 나뉘었습니다. 하지만 관찰만으로 판단하기보다, 강제 종료 시점을 바꿨을 때도 같은 종류의 실패가 발생하는지 확인하고 싶었습니다.

같은 APK와 기존 위젯을 유지한 채 추가 실험을 진행했습니다.

매번 설치 전에 앱을 강제 종료하고 APK를 재설치했습니다. 앱 데이터는 지우지 않았고, 위젯을 다시 등록하거나 액티비티를 실행하지도 않았습니다.

변경한 것은 **설치가 반환된 뒤 추가로 강제 종료하는지, 한다면 얼마나 기다리는지**였습니다.

| 설치 후 추가 동작 | 횟수 | 관찰 결과 |
|---|---:|---|
| 강제 종료 없음 | 2회 | 모두 `Available` 콘텐츠 제공 |
| 즉시 강제 종료 | 2회 | 모두 종료 이후 업데이트가 생성돼 콘텐츠 제공 |
| 50ms 대기 후 강제 종료 | 2회 | 대기 중 전달 대상 제거 또는 실행 중 프로세스 종료 |
| 500ms 대기 후 강제 종료 | 1회 | 실행 중 프로세스 종료 |

이 실험은 Android Studio의 배포 과정을 그대로 복제한 것은 아닙니다. 같은 APK의 패키지 교체와 강제 종료 순서를 따로 확인한 실험입니다. 결과는 콘텐츠 제공 로그와 프로세스·패키지 상태로 판정했으며, 매번 화면까지 확인한 것은 아닙니다.

여기서 50ms가 실패 임계값이라는 뜻은 아닙니다. 적은 횟수의 실험이고, 지연값도 해당 환경에서 지정한 값입니다.

확인하려던 것은 시간값 자체보다 **업데이트가 어느 단계에 있을 때 실행이 끊기는가**였습니다.

### 업데이트가 전달되기 전에 끊기는 경우

한 실험에서는 다음 순서가 관찰됐습니다.

```text
23:14:22.037  업데이트 대기열 진입
23:14:22.076  강제 종료
```

이후 브로드캐스트 기록에는 전달 시각과 수신자가 남아 있지 않았고, 새 앱 프로세스도 시작되지 않았습니다.

업데이트가 대기 중일 때 강제 종료가 발생하면서 전달 대상이 제거되는 경우였습니다.

### 처리를 시작한 뒤 끊기는 경우

다른 실험에서는 앱 프로세스가 시작된 뒤 종료됐습니다.

```text
23:15:04.955  업데이트 대기열 진입
23:15:05.070  앱 프로세스 시작
23:15:05.108  강제 종료
23:15:05.109  앱 프로세스 종료
```

이번에는 전달 이전에만 문제가 생긴 것이 아니었습니다. 업데이트를 처리할 프로세스가 시작돼도, 처리 도중 강제 종료되면 콘텐츠 제공까지 이어지지 못했습니다.

따라서 “업데이트를 전달받았는가”만으로 성공을 판단할 수도 없었습니다. **실행이 시작됐는지와 끝까지 이어졌는지를 함께 확인해야 했습니다.**

## 그렇다면 초기화 수정은 효과가 있었을까?

강제 종료로 실행이 중단되는 경우를 찾았지만, 그것만으로 이전 수정의 효과까지 입증되는 것은 아닙니다.

초기화 위치를 옮긴 수정이 실제로 차이를 만드는지도 따로 확인해야 했습니다.

이번에는 설치 후 추가 강제 종료를 제외하고 원본과 수정본을 비교했습니다. 실행 중단 변수를 제외한 상태에서 초기화 경로를 보기 위해서였습니다.

Android 11의 같은 에뮬레이터에서 기존 위젯을 유지했고, 두 코드에 같은 형태의 진단 로그를 추가했습니다. 빌드 설정과 Glance 버전도 동일하게 맞췄습니다.

과거의 개발 환경 전체를 복원한 실험은 아닙니다. 같은 빌드 환경에서 원본과 수정본의 날씨 위젯 로직을 비교했습니다.

### 원본

핵심 로그에서 시각과 위젯 ID를 생략하면 다음과 같습니다.

```text
original onUpdate
original WeatherRepo INIT state=Loading
original provideGlance ENTER state=Loading
original provideContent state=Loading
original Content committed state=Loading
```

`provideGlance()`까지 실행됐지만, 데이터 갱신 함수는 호출되지 않았습니다. 이후 화면에서도 로딩 표시가 유지됐습니다.

### 수정본

```text
fixed onUpdate
fixed WeatherRepo INIT state=Loading
fixed provideGlance ENTER state=Loading
fixed updateWeatherInfo ENTER
fixed updateWeatherInfo EXIT state=Available
fixed provideContent state=Available
fixed Content committed state=Available
```

수정본에서는 `provideGlance()`에 진입한 뒤 데이터 초기화가 실행됐고, `Available` 상태로 콘텐츠를 제공했습니다. 실제 화면에도 날씨가 표시됐습니다.

| 비교 항목 | 원본 | 수정본 |
|---|---|---|
| `onEnabled()` | 호출되지 않음 | 호출되지 않음 |
| `provideGlance()` | 호출됨 | 호출됨 |
| 데이터 초기화 | 실행되지 않음 | 실행됨 |
| 최종 상태 | `Loading` | `Available` |

두 경우 모두 `onEnabled()`가 호출되지 않았다는 조건은 같았습니다. 차이는 실제로 실행되는 `provideGlance()` 경로에서 데이터를 초기화하는지였습니다.

각 코드에서 유효한 재설치 관찰은 1회씩입니다. 이 결과를 모든 환경의 성공률로 해석할 수는 없습니다.

다만 **관찰한 실행 경로에서 원본은 초기화가 빠졌고, 수정본은 그 누락을 보완했다는 차이**는 확인할 수 있었습니다.

## 두 문제를 구분하고 나니

처음에는 수정한 코드에서도 같은 로딩 화면이 나왔기 때문에, 기존 원인 분석부터 다시 의심했습니다.

추가 조사 후에는 실패를 두 가지로 구분할 수 있었습니다.

| 구분 | 초기화 누락 | 업데이트 전달·처리 중단 |
|---|---|---|
| 관찰한 실행 | `provideGlance()`까지 실행 | 전달 전에 끊기거나 처리 도중 프로세스 종료 |
| 데이터 로딩 | 실행 경로에 초기화 호출이 없음 | 초기화 코드가 실행될 기회 또는 실행 시간이 보장되지 않음 |
| 이전 수정의 효과 | 누락된 초기화를 수행 | 강제 종료 자체는 막지 못함 |

초기화 위치를 옮긴 수정은 의미가 있었습니다. 그러나 그 수정으로 재설치 과정에서 발생하는 모든 무한 로딩을 해결했다고 말할 수는 없었습니다.

[PR #431](https://github.com/android/platform-samples/pull/431)은 이후 병합됐습니다. 초기화 누락을 수정한 코드는 공식 샘플에 반영됐지만, 추가 조사에서 관찰한 실행 중단은 별도로 설명해야 하는 문제였습니다.

## 아직 설명하지 못한 것

이번 조사로 데스크탑의 Android 11에서 성공과 실패가 갈린 일부 실행은 설명할 수 있었습니다.

하지만 처음 조사를 시작하게 만든 **환경별 차이 전체를 설명한 것은 아닙니다.**

맥북에서는 정상 동작을 확인하기 쉬웠는데 왜 데스크탑에서는 그렇지 않았는지, Android 11과 더 높은 버전 사이에 어떤 차이가 결과에 영향을 줬는지는 아직 확인하지 못했습니다.

이를 비교하려면 Android 버전 외에도 Studio와 에뮬레이터 버전, CPU 아키텍처, 호스트 부하와 배포 시점 같은 조건을 함께 확인해야 합니다. 이번 Android 11의 관찰을 다른 버전과 기기의 실패 원인으로 그대로 적용할 수는 없습니다.

또한 “WorkManager에 작업이 전달되기 전에 종료돼서 실패했다”는 경계까지 입증한 것도 아닙니다. 직접 확인한 것은 위젯 업데이트의 대기·전달 기록과 앱 프로세스의 시작·종료 순서였습니다.

설명할 수 있는 범위는 그 관찰까지입니다.

## 마무리

이번 조사는 맥북에서 확인한 수정이 다른 환경에서도 동작하는지 확인하려는 데서 시작했습니다.

다른 Android 버전에서 실패했고, 같은 Android 11에서도 결과가 달랐습니다. 처음에는 이것이 기존 수정이 잘못됐다는 신호처럼 보였습니다.

하지만 로그를 따라가 보니 같은 로딩 화면 안에 서로 다른 실패가 있었습니다. 어떤 실행에서는 데이터를 초기화하지 않았고, 어떤 실행에서는 위젯 코드가 시작되지 않거나 처리 도중 종료됐습니다.

이전 수정이 해결한 것은 첫 번째 문제였습니다.

이번에는 날씨가 표시됐는지만 확인하는 데서 그치지 않고, 업데이트가 전달됐는지, 프로세스가 시작됐는지, 초기화가 실행됐는지를 나눠 확인했습니다.

**수정 후에도 증상이 남는다는 사실만으로 수정이 무효인 것은 아니었습니다. 반대로 한 환경에서 성공했다는 사실만으로 해결 범위를 넓혀서도 안 됐습니다.**

어디까지 실행됐고 어디서 끊겼는지 확인하고 나서야, 고친 문제와 남은 문제를 구분할 수 있었습니다.
